# ClipPacks guide

ClipPacks is a collection of reusable, ready-to-import AI agent teams and organization templates for Paperclip. Packs are independent import assets; the ClipPacks repository name remains unchanged.

## Reuse one organization across projects

A roster is reusable; project authority is not. Keep one verified organization roster instead of cloning or auto-hiring the same agents for every project. For each assignment, provide the exact project/repository, task owner, allowed files, objective, constraints, acceptance criteria, and verification evidence. Confirm the registered agent identity, organization membership, and task ownership from current Paperclip records. Do not infer permission or isolation from a name, manager link, prompt, or project selector. Do not let one project assignment change another project's agents, tasks, permissions, or workspaces.

Follow [installation.md](installation.md) when importing the first pack. Import into a new organization with `pauseAutomations: true`; inspect actual status and effective grants before any activation or work assignment.

## Add a pack

Keep each pack self-contained under `packs/<pack-name>/`. Its distributable archive should have the importer package at the archive root, normally including:

- `.paperclip.yaml` and `COMPANY.md`;
- one standalone `agents/<slug>/AGENTS.md` for each intended role;
- a pack `README.md`, `TEAM.md`, `VALIDATION.md`, and `LICENSE.md` describing actual scope, evidence, and attribution.

Keep project paths, credentials, private IDs, environment values, and machine-specific runtime state out of reusable packs. Do not invent importer fields or claim that prompts/reporting links provide authorization, execution isolation, or skill loading. Preserve upstream notices for copied/adapted material, identify source and version accurately, and distinguish source references from files actually included in the pack.

The first pack retains upstream ACON references such as `.agents/reference/crew/...` and `.agents/skills/...` as provenance/context pointers; those references are not packaged runtime files and do not prove that Paperclip loads them. Its preserved `VALIDATION.md` contains a source-relative link into the ACON repository. That link resolves in upstream ACON source context, not within ClipPacks; it is intentionally preserved byte-for-byte and is neither an import-schema path nor a runtime dependency. For public provenance, see [ACON's crew reference](https://github.com/HairyBlue/acon/blob/master/.agents/reference/crew/README.md). Do not add placeholder files or copy ACON source into this repository to make those source-context references appear local.

## Validate a pack

Before publishing, check the exact archive entry inventory, paths, file types, duplicate/case-colliding names, content hashes, manifest fields, standalone role instructions, support-doc bytes, license notices, and all pack-local links. Classify inherited upstream provenance references as source context rather than import/runtime dependencies; do not silently rewrite preserved upstream files. State what was actually tested and list unverified importer/runtime, permission, pause, model, and workspace behavior plainly.

## Publish a pack-specific release asset

After a reviewed repository commit has been pushed through the separately authorized GitOps process, publish a GitHub Release (the first planned version is `v0.1.0`) and attach the existing pack-specific archive as a release **Asset**, with its package filename (for the first pack, `paperclip-acon-team.zip`). Attach the pack ZIP itself, not GitHub's autogenerated monorepository **Source code (zip)**. The asset should contain the pack contents at its archive root, without an enclosing `ClipPacks/` or `packs/<name>/` directory. Never imply that release publication performs an import, pauses agents, grants permissions, or activates a team. No release, workflow, or Paperclip operation is performed by these instructions.
